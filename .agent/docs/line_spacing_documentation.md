# توثيق آلية تباعد الأسطر ومعالجة النصوص (Line Spacing & Text Rendering)

يُعتبر ضبط تباعد الأسطر ليطابق برنامج Microsoft Word تماماً تحدياً تقنياً كبيراً نظراً لاختلاف محركات العرض (Rendering Engines) بين Flutter و Word. تشرح هذه الوثيقة الآلية المعتمدة حالياً، التحسينات التي تمت، والتفاصيل الدقيقة التي يجب الانتباه لها.

## 1. الآلية الأساسية (Core Mechanism)

نعتمد في `SelectableText.rich` على خاصية **`StrutStyle`** (دعامة السطر).
- **الوظيفة:** تقوم `StrutStyle` بفرض "ارتفاع أدنى" ثابت لكل سطر في الفقرة، بغض النظر عن محتوى السطر (سواء كان يحتوي على تشكيل، أحرف مرتفعة، أو صور). هذا يضمن تناسق الفقرة ويمنع تداخل الأسطر.

### المعادلة الحسابية للارتفاع
يتم حساب ارتفاع السطر وفق المعادلة التالية:

```dart
LineHeight_Px = (MaxFontSize) * (LineMultiplier)
```

حيث أن:
1.  **`MaxFontSize`**: هو أكبر حجم خط مستخدم في أي "مقطع نصي" (Run) داخل الفقرة الواحدة.
2.  **`LineMultiplier`**: هو معامل التباعد.
    *   للنصوص العربية (مثل `Traditional Arabic`)، نستخدم معامل تصحيح **`1.30`** بشكل افتراضي للتباعد المفرد (Single Spacing).
    *   هذا المعامل ضروري لأن الخطوط العربية تحتوي على تشكيل (فتحة، كسرة، شدة) وصواعد وهوابط تتطلب مساحة رأسية أكبر مما يوفره الـ Metrics القياسي للخط.

## 2. التحسينات الأخيرة (Recent Improvements)

### مشكلة تداخل الأسطر (The Overlap Issue)
**المشكلة:** في بعض الفقرات، كانت الأسطر تتداخل ببعضها البعض رغم وجود `StrutStyle`.
**السبب:**
*   كانت الـ `StrutStyle` تأخذ حجم الخط من "خصائص الفقرة الافتراضية" (`pPr`).
*   اكتشفنا أن ملف الـ XML قد يحدد حجم خط صغير جداً للفقرة (مثلاً `13.5pt`)، بينما النصوص *داخل* الفقرة محددة بحجم كبير (`20pt`).
*   النتيجة: الدعامة (`Strut`) كانت تُبنى على ارتفاع `13.5`، بينما النص الفعلي يحتاج ارتفاع `20`، مما أدى إلى "فيضان" النص خارج الدعامة وتداخله مع السطر التالي.

**الحل (Max Font Size Calculation):**
تم تعديل الكود في `Paragraph.dart` ليقوم بمسح شامل لجميع مقاطع النص (`runs`) داخل الفقرة قبل العرض، واستخراج **أكبر حجم خط** مستخدم.
```dart
double maxFontSize = prPr?.fontSize ?? 14.0;
for (var run in textRunTs) {
  if (run.rpr?.fontSize != null) {
    if (run.rpr!.fontSize! > maxFontSize) {
      maxFontSize = run.rpr!.fontSize!;
    }
  }
}
// ثم يتم استخدام maxFontSize هذا في StrutStyle
```

## 3. تنبيهات هامة و "خادعات" (Red Herrings)

أثناء العمل، واجهنا أموراً قد تظن أن لها علاقة بالمشكلة، ولكنها مضللة:

### أ. خصائص الفقرة مقابل خصائص النص (Paragraph Mark vs. Text Run)
*   **الملاحظة:** في ملف XML، قد تجد `w:pPr` يحتوي على لون (مثلاً أخضر) وحجم خط غريب.
*   **الحقيقة:** هذه الخصائص غالباً ما تطبق على **علامة الفقرة المخفية (Pilcrow ¶)** وليس على النص نفسه.
*   **الخطأ السابق:** كنا نقوم بدمج هذه الخصائص مع النص، مما أدى لظهور النص بلون أخضر وحجم خطأ في التطبيق.
*   **التصحيح:** يجب فصل "تنسيق الفقرة المباشر" عن "تنسيق النص". النص يرث فقط من **الستايل (Style)**، ولا يرث اللون/الحجم من خصائص علامة الفقرة المباشرة.

### ب. معامل التباعد (1.15 vs 1.30)
*   برنامج Word (نسخة 2007 وما بعد) يستخدم افتراضياً تباعد `1.15`.
*   لكن للخطوط العربية، هذا التباعد غالباً ما يسبب قص التشكيل. الاستقرار كان على `1.30` كقيمة آمنة ومقاربة بصرياً للتباعد "المفرد" المريح في Word مع الخط التقليدي.

## 4. الخلاصة للرجوع المستقبلي

1.  **دائماً احسب `StrutStyle` بناءً على المحتوى الفعلي:** لا تعتمد على القيم الافتراضية للفقرة فقط، فالنص قد يتجاوزها.
2.  **تجاهل تنسيقات `pPr` المباشرة للنصوص:** إلا إذا لم يكن للنص أي تنسيق خاص به ولا أي ستايل (وهو نادر). العلامة `¶` لها تنسيقها الخاص.
3.  **المحاذاة الرأسية:** الـ `StrutStyle` القوي يحل 90% من مشاكل المحاذاة، لكنه يتطلب ضبطاً دقيقاً للمعامل (`Multiplier`) حسب نوع الخط.
